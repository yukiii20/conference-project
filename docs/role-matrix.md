# Role matrix (Step 7, section 4)

Built from the real permission system, not assumptions:
- `database/02_reference_data.sql` (roles, permissions, `role_permissions` seed — the only place role→permission mappings are defined; there is no per-member permission override table, so every `manager` gets the same fixed set).
- `server/src/middleware/auth.ts` (`requireAuth`, `requireConferencePermission`, `requireConferenceRole`, `assertConferencePermission` — platform admins bypass every permission check).
- Every `server/src/modules/*/routes.ts` file's actual middleware per route.
- Frontend: `src/lib/roles.ts`, `src/pages/portal/sidebarConfig.ts`, `src/pages/convenor/sidebarConfig.ts`, `ConvenorSidebar.tsx`, `PeopleSection.tsx`, `SignInForm.tsx`, `ProtectedRoute.tsx`, `server/src/app.ts` (`blockWritesInAdminViewAsMode`).

Permission set per role, from `database/02_reference_data.sql` lines 44-52:
- **convenor**: every permission.
- **manager**: every permission *except* `members.manage` and `audit.read`.
- **staff**: `conference.view_internal`, `registration.read_all`, `attendance.record` only.
- **reviewer / session_chair / speaker / author**: no conference-wide permission rows at all — access is entity-scoped (their own assignment/session/submission), enforced in each service function, not via `role_permissions`.
- **admin** (platform role, `platform_user_roles`): bypasses `assertConferencePermission` entirely (`isPlatformAdmin` short-circuit in every guard).

## Mismatches found

Ranked by severity — security/permission bugs first, then UX dead-ends, then cosmetic.

### 1. (UX dead-end, misleading) Manager sees a "Role requests" tab and a badge count for something they're forbidden to do
- **Where:** `src/pages/convenor/sidebarConfig.ts:36-41` — the `people` section's tabs are `requests`, `members` (`hideForManager: true`), `committees`, `speakers`. Only `members` is hidden for managers; `requests` is not.
- **Backend:** `server/src/modules/roleRequests/service.ts:47` (`listRoleRequests`) and `:77`/`:147` (`approveRoleRequest`/`rejectRoleRequest`) all call `assertConferencePermission(actorUserId, conferenceId, 'members.manage')` — a permission `manager` does not hold (`database/02_reference_data.sql:48`, `manager` is granted every permission *except* `audit.read` and `members.manage`).
- **Compounding:** `server/src/modules/dashboard/routes.ts:7` requires only `conference.view_internal` (which manager *does* hold), so the People sidebar item's red badge (`ConvenorPage.tsx:110` → `pendingRoleRequests`) actively shows managers a count of role requests they cannot approve or even view — `PeopleSection.tsx:17-33` renders `RoleRequestsTab` as the `requests` tab's element, which will 403 the moment a manager opens it.
- **Impact:** a manager is drawn toward a tab that always fails. Not a security hole (the server correctly rejects it), but exactly the "dead button that ends in 403" the audit brief calls out.
- **Fix direction:** add `hideForManager: true` to the `requests` tab in `sidebarConfig.ts`, and exclude `pending_role_requests` from the People badge count when `isManager` (or only show the badge for tabs the manager can actually open).

### 2. (Needs verification, not confirmed) View-as-admin read-only relies on native `<fieldset disabled>` semantics
- **Where:** `src/pages/ConvenorPage.tsx:225` wraps all convenor routes in `<fieldset disabled={Boolean(viewAs)}>`. Native HTML `disabled` propagation only reaches real form controls (`button`, `input`, `select`, `textarea`, nested `fieldset`) — it does **not** disable a non-form element (e.g. a `<div onClick>` custom control, or a component that fires a request from a `useEffect`/drag-and-drop handler rather than a disabled-aware element).
- **Why flagged, not fixed:** server-side `blockWritesInAdminViewAsMode` is the real enforcement and was confirmed correctly applied globally (finding above), so this is strictly defense-in-depth, not a security hole. But it's worth an explicit pass over `ImageUpload.tsx` and any drag-and-drop/file-picker components used inside the convenor portal to confirm every trigger is a real disabled-aware form control, since a stray enabled control would be confusing (button appears clickable, request still gets rejected with a 403 toast) even though nothing unsafe happens.
- **Fix direction:** spot-check `ImageUpload.tsx` and any custom dropdown/drag-drop widgets render a native disabled control when `viewAs` is active; add a visual "read-only" affordance (cursor, opacity) if any don't.

No `role_code`/permission mismatches were found beyond #1 — every other route's guard matches what `database/02_reference_data.sql`'s `role_permissions` seed grants that role, and every frontend sidebar/tab correctly mirrors the corresponding backend check (staff, reviewer, session_chair, author scoping, blind-review author stripping, and private file downloads were all traced to a concrete server-side ownership or permission check, not just a hidden button).

## Fixed

1. **Manager "Role requests" dead-end — FIXED.** `src/pages/convenor/sidebarConfig.ts`: added `hideForManager: true` to the `requests` tab (now matches `members`). `src/pages/convenor/ConvenorSidebar.tsx`: the People badge now passes `0` for a manager instead of `pendingRoleRequests`. `src/pages/convenor/DashboardTab.tsx` (and `src/pages/ConvenorPage.tsx`, which now threads `isManager` into it): the "Needs your attention" card no longer shows a "Pending role requests" row to a manager. Verified visually — see `test-results/ui-after/manager-1280.png` vs `convenor-dashboard-1280.png`: the convenor sees the badge and attention row, the manager (same conference, same data) sees neither.
2. **View-as-admin read-only gap in `ImageUpload`'s drag-and-drop zone — FIXED.** Added `src/lib/adminViewAsContext.tsx` (a tiny context, `AdminViewAsProvider`/`useIsAdminViewAsReadOnly`), provided from `ConvenorPage.tsx` alongside the existing `<fieldset disabled>`. `ImageUpload.tsx` now reads it and folds it into its existing `busy` flag (disables the Upload/Remove buttons, which `<fieldset>` already covered) and, newly, ignores `onDrop`/`onDragOver` while read-only (which `<fieldset>` could never reach, since it isn't a form control). No other drag-and-drop widgets exist in the app (confirmed by `grep -r "onDrop|onDrag" src`).
